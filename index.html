The problem

The evidence is deleted before anyone asks for it

Jenkins rotates build records — most jobs keep a handful. Playwright’s HTML report, Allure and JUnit each show exactly one build. So the three questions a team actually arrives with are all unanswerable by the time they are asked.

“Has TC-1042 ever passed?” Or has it been red since the day it was written and nobody noticed?
“Did my fix actually work?” Or did that one run just get lucky on a flaky test?
“Is this 26 problems, or 4?” Forty red tests could be one broken selector. Nothing distinguishes them.

Engineering notes

Decisions and their costs

Every one of these is a trade, not a free win.

One immutable JSON file per build

Not a growing database. Each build writes only its own file and never reads or rewrites another’s. That single constraint buys crash-safety, idempotency and concurrency-safety without a line of locking code — a build that dies mid-write corrupts at most its own file, and re-running build #142 replaces #142 and nothing else.

Cost: reading the history means opening every file. At a few thousand builds that becomes worth revisiting; at a few hundred it is instant.
Parse the JUnit file, not the CI API

An API-driven reporter can only see what the server still remembers — which puts you straight back where you started. Reading the file on disk captures build #142’s data at build #142, and makes the tool work identically on GitHub Actions, GitLab CI or a laptop.

Cost: you must run it as a step inside the job. There is no way to bolt it on from outside after the fact.
Zero dependencies, including the XML parser

The consumer is a shell step on a build agent someone else administers. Every dependency is a thing that can fail to install, pull a CVE, or need a lockfile committed to a repo that is about tests, not tooling.

Cost: a regex-based XML reader rather than a real parser. Only acceptable because the input shape is narrow and every assumption it makes is pinned down by a test. If this had to accept arbitrary XML, the trade would be wrong.
—init is opt-in, and must be removed

A missing store directory is an error, not something to silently fix. If a job later runs on an agent where the history volume is not mounted, auto-creating it would start an empty history and nobody would notice until they went looking for a trend that no longer existed.

Failing loudly is the correct behaviour. --init is the one-time opt-in, and the docs are blunt about taking it back out.

Cost: one extra step during setup, and one more thing to explain.
Environment chips carry a label, not just a colour

Colour alone does not survive a greyscale print, a compressed screenshot pasted into chat, or the roughly 8% of men who cannot separate orange from green — which is exactly the staging/production pair. Each chip carries a four-letter cap as well as its colour.

Cost: ~24px of row width, and a build column too narrow for a chip needs a second, smaller treatment of the same information.
The interesting bug

A reporting bug that produces plausible output

Every failure became its own “root cause”

An early version read the first CDATA block anywhere inside <testcase>. On any suite that logs to stdout, that is <system-out> — so every signature picked up a unique timestamp, every group had exactly one member, and the cause table degenerated into one row per test.

The page still rendered. The table still had rows. It looked like it was working — and it was worse than useless, because it appeared to be triaging while telling you nothing at all.

The fix is three lines: scope the read to the <failure> element and skip logger-formatted lines. The lesson is the part worth keeping — a reporting bug that produces plausible output is far more dangerous than one that crashes, because nothing prompts you to check it. That is most of why test/signature.test.js exists, and why the report states inside the report that its grouping is mechanical rather than diagnostic.
